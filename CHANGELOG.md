## [Unreleased]

### Added

- **Backend drives the ERC-8183 escrow for paid A2A jobs (C3).** On a chain with `AGENT_JOB_ESCROW_ADDRESS_<chainId>` (+ `ESCROW_EVALUATOR_PRIVATE_KEY`), a paid job is USDC-only (D8) and its budget is escrowed on-chain: the requester's wallet runs `createJob → setBudget → approve → fund` through the transaction queue (`TxType ESCROW_LOCK`, `metadata.erc8183`, `intentId = erc8183:<step>:<jobId>`), the provider's `PATCH COMPLETED` becomes `submit(jobId, keccak256(result))` (`TxType ESCROW_SUBMIT`), and the operator evaluator (D5, new `services/escrow/evaluator-signer.ts`) settles from the new BullMQ queue `escrow-settlement` with `complete` (or `reject` after `POST /v1/jobs/:id/contest`), committing the ERC-8004 feedback file hash in `optParams` and serving the file at the public `GET /v1/jobs/:id/feedback.json` (R3 backend half; canonical JSON so `keccak256(body)` matches the on-chain hash). Cancellations unwind a locked budget through an evaluator `reject`; a repeatable sweep calls `claimRefund` after `expiresAt`; the payment-recovery scan never DB-refunds an escrow job. `ACCEPTED` requires `escrow.onChainStatus = FUNDED` (`409 ESCROW_NOT_FUNDED`). Job responses gain an `escrow` object; migration `0014_erc8183_escrow` adds the `Job` escrow columns and `ESCROW_SUBMIT`. Orchestrator `services/job/escrow-erc8183.service.ts` is pure (injected deps) and wired by `escrow-erc8183.runtime.ts`. ABIs generated by the new `scripts/gen-abi.mjs` (`npm run abi`, `abi:executor`, `abi:escrow`) into `abi/AgentJobEscrow.abi.ts` / `abi/ReputationHook.abi.ts`; Base Sepolia USDC added to the token registry. Env: `ESCROW_JOB_TTL_SECONDS`, `ESCROW_EVALUATION_DELAY_SECONDS`, `BACKEND_PUBLIC_URL`. Docs: `erc-8183-mapping.md` §6, deployment guide env table; OpenAPI + generated types. 95 new unit tests (`escrow-erc8183.service.test.ts`, `jobs.routes.erc8183.test.ts`, `abi.erc8183.test.ts`, `payment-recovery.erc8183.test.ts`, extensions of the worker/guard/finalizer suites).
- **Job-scoped x402 payments: `POST /v1/jobs/:id/pay-resource` + MCP `pay_for_resource` (P2, with the P5 ledger state machine).** The job's **provider** pays a third-party HTTP 402 resource with its own USDC, within the job's remaining reward budget (`reward − Σ reserved/pending/settled/unknown payments`); the requester gets `403`, a job that is not `ACCEPTED` gets `409`, and only USDC-denominated jobs qualify (`400 UNSUPPORTED_BUDGET_TOKEN` — no oracle conversion). The cap (remaining budget, lowered by the caller's `maxAmount`) is handed to `X402ClientService`, so an above-cap price is refused **before anything is signed** (`402 BUDGET_EXCEEDED` with `price`/`remaining`/`cap`); only USDC on the job's chain is accepted (`400 UNSUPPORTED_ASSET`). Every attempt is a durable `ResourcePayment` row (migration **0016**, model at the end of `schema.prisma`; `(jobId, paymentId)` unique) with the state machine `reserved → pending → settled | unknown | refused` plus `failed_before_signing`: the row is reserved under a `Job` row lock before signing (concurrent payments cannot overspend), the EIP-3009 nonce is recorded before the signed payload leaves, a timeout / transport error after signing is `unknown` (502 `PAYMENT_OUTCOME_UNKNOWN`, counted against the budget, logged for the operator, **never retried automatically**), and an `offer-receipt` that does not verify still settles but is stored `receiptVerified: false`. Idempotent per `paymentId` (sent to the server through the x402 `payment-identifier` extension): a retry returns a `pending`/`settled`/`unknown` row without a second payment; `refused`/`failed_before_signing` rows are retried on the same row. The URL is stored without query string or userinfo; the signed authorization is never echoed. `X402ClientService` gained the `onBeforeSign` / `onAuthorizationSigned` ledger hooks (a throw aborts before signing / before sending); the P1 fake-facilitator harness moved to `src/__tests__/helpers/x402-fixture.ts`; the token registry gained Base Sepolia USDC. New `services/payments/resource-payment.service.ts`, `api/routes/resource-payments.ts`; the MCP client now throws a typed `ApiError` so the tool returns `BUDGET_EXCEEDED` / `PAYMENT_OUTCOME_UNKNOWN` details as structured output. OpenAPI + generated types, `docs/api-reference.md`, `docs/architecture/x402-payments.md` §10. 25 route tests + 2 hook tests. Not included: reconciliation of `unknown` rows (`unknown → settled`), the `mppx` dialect (P4), facilitator configuration (P3).
- **x402 buyer-side client (P1).** New `X402ClientService.payResource()` (`packages/backend/src/services/payments/x402-client.service.ts`) fetches a URL, and when it answers `402` with x402 v2 requirements, signs an EIP-3009 / Permit2 authorization with the agent's wallet and retries with `PAYMENT-SIGNATURE` — under three spend gates (`maxAmountUsd` per call, `allowedNetworks` CAIP-2 filter, optional `paymentId` idempotency). Only payment-specific failures throw (`BudgetExceededError`, `NoAcceptableSchemeError`, `PaymentFailedError`); non-402 responses are returned untouched. Both wallet providers gained `signTypedData` (`services/wallet/signer.ts` adapts a `walletId` into the `{ address, signTypedData }` surface x402 needs; Turnkey signs the EIP-712 hash via `signRawPayload`). New `config/x402.ts` (per-chain facilitator defaults, `X402_FACILITATOR_URL` override). Deps: `@x402/core`, `@x402/evm`, `@x402/extensions`, `@x402/fetch` **2.28.0**; viem resolved to 2.57. Docs: `docs/architecture/x402-payments.md`. 40+ unit tests across `x402-client.service.test.ts`, `wallet.signer.test.ts`, `x402.config.test.ts`.
- **ERC-8183 job escrow + ERC-8004 reputation hook (C2, contract half).** `packages/contracts/src/AgentJobEscrow.sol` implements the ERC-8183 (Agentic Commerce) job escrow verbatim — client funds a job in one ERC-20, provider submits, evaluator completes (release minus `platformFeeBP`) or rejects (full refund); permissionless `claimRefund` after expiry; per-job `IACPHook`; the operator can only pause creation/funding. `ReputationHook.sol` is an `IACPHook` that writes ERC-8004 `giveFeedback` for the provider in the same tx as `complete`/`reject` and never blocks settlement. `IACPHook.sol` / `IReputationRegistry.sol` interfaces, `script/DeployEscrow.s.sol` (Base Sepolia first; USDC + registry defaults per chain), mocks, and Foundry suites `AgentJobEscrow.t.sol`, `ReputationHook.t.sol`, `DeployEscrow.t.sol`. `docs/operations/contract-deployment.md` gained the escrow deployment section.
- **MCP tool annotations on every tool (S2).** All 32 `@agent_fi/mcp-server` tools now list a `title` and the four MCP annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) from one reviewed table, `packages/mcp-server/src/annotations.ts`, with a one-line justification per tool: 14 read-only tools; 15 fund-moving tools (swaps, transfers, Aave/Compound/ERC-4626, Curve, GMX, `pay_agent`, `pay_for_resource`, `post_job`, `update_job_status`) are destructive, open-world and not idempotent; `update_policy`, `set_my_manifest` and `sign_handshake` are classified individually (`sign_handshake` is not read-only — it uses the wallet's signing authority). The backend's own `/mcp/sse` surface (18 proxy tools) now requires and lists annotations too; `mcp.annotations.test.ts` fails if a proxy tool disagrees with its stdio counterpart. `tools/list`, `tools/call` and the registry moved from `index.ts` to `server.ts`. The package gained a vitest suite (`npm test`, 59 tests: annotation coverage both ways, sanitizer rules, `tools/call` against a stubbed backend, a real stdio round-trip) and CI runs it in the new **MCP Tests** job; `npm run build` uses `tsconfig.build.json` so tests stay out of `dist/`.

### Fixed

- **The stdio MCP server no longer writes to stdout at startup (found by S2).** `api-client.ts` loaded `dotenv/config`, and dotenv 17 prints `◇ injected env (n) from .env // tip: …` to stdout via `console.log` — on the stdio transport stdout is the JSON-RPC channel, so every client saw a non-JSON line before `initialize`. It now calls `config({ quiet: true })`; `stdio.test.ts` spawns the server and fails on any non-JSON-RPC stdout line.
- **Admin resume re-activates the DB policy the pause deactivated (A3b).** Resuming an agent through the `POST /admin/agents/:id/pause` toggle only flipped `agent.active`; `AgentPolicy.active` stayed `false`, so the agent remained blocked by `PolicyService.validateTransaction` and the worker's pre-submit guard until someone remembered a `PATCH /v1/agents/:id/policy`. The pause now stamps `AgentPolicy.pausedByOperatorAt` (migration `0017_policy_pause_marker`) when it deactivates an *active* policy, and resume re-activates the policy only while that stamp is present, then clears it — a policy that was already inactive before the pause (agent soft-delete via `DELETE /v1/agents/:id`, `PATCH active=false`, or a pause that predates the stamp) stays inactive and the response says so. Any explicit `active` write through `PolicyService.setPolicy` and the soft-delete path clear the stamp, so a later resume can never undo a deactivation it did not cause. New explicit, idempotent `POST /admin/agents/:id/resume` (same `{ syncOnChain }` body; no-op on an agent that is not paused); both resume paths answer `{ active: true, agentReactivated, policyReactivated, policyNote, onChainSync }` where `onChainSync` carries `AgentPolicyModule.resume(safe)` calldata on request. The pause response is unchanged. The admin dashboard's Pause/Resume button shows `policyNote` when the policy was left inactive. OpenAPI (`ResumeAgentResponse`, `PausedAgentResponse`, `Policy.pausedByOperatorAt`) and generated types updated. 24 new tests in `admin.pause.routes.test.ts` (route + pre-submit guard end to end, calldata decoded against the ABI) and `policy.service.test.ts`.
- **No mock simulation can authorise a transaction in production or staging (A2).** `SimulatorService` used to return an always-success stub whenever Tenderly was not configured — in every environment. Now, without Tenderly, `NODE_ENV=production`/`staging` run a real `eth_call` dry-run (viem `estimateGas` against the chain RPC, provider `'eth_call'`): a revert is a failed simulation with the reason, an RPC/transport failure throws `Simulation service unavailable … Transaction blocked for safety`, and only `development`/`test` keep the mock (`provider: 'mock'`, `_isMock: true`). New `services/transaction/simulation-guard.ts` (`isSimulationUsable` / `assertSimulationUsable` / `ensureSimulationUsable`) is called by every transaction route and the A2A payment path as defense in depth: a mock result in a production-like environment is refused with `503 { error: "Simulation unavailable in production" }`. `env.ts` logs a WARN at boot when production runs without Tenderly. `simulator.service.test.ts` covers all providers and the guard.
- **Review follow-ups to A1/A2/A3/S1 (`fix/review-r1-backend`).**
  - *S1 bypass (P1):* an agent could `PATCH` `maxValuePerTxEth: ""` (or `"  "`, `"1e3"`, `"0x10"`, `"5abc"`, `"unlimited"`): the tighten-only classifier read it with `Number()` (→ `0`, "tightening") while `PolicyService` enforced with `parseFloat()` (→ `NaN`, no limit). Both halves now share one parser (`services/policy/policy-numbers.ts` — `parsePolicyDecimal`, where an unparsable value is *unlimited* and therefore always loosening), and the API edge (`createAgentSchema`, `updatePolicySchema`, `POST /v1/public/agents`, the MCP `update_policy` tool) only accepts the strict pattern `^\d+(\.\d+)?$` — anything else is `400`. Zod failures on these routes are now `400 { error: "Validation failed", details }` instead of an unhandled 500.
  - *A3 regression (P1):* the worker wrote `status: SUBMITTED` **before** broadcasting. A broadcast failure left the row `SUBMITTED` without a hash, every BullMQ retry was skipped by the new pre-submit guard, the permanent-failure handler (FAILED + dead-letter + A2A finalize) never ran, and an A2A payment stayed `PAYMENT_PENDING` with its reservation locked. The tx now stays `QUEUED` while broadcasting and `{ status: 'SUBMITTED', txHash }` is written in one update after `submit()` resolves, so idempotency rests on the hash the guard already checks. Processor and failure handler were extracted into `queues/transaction.processor.ts` (`processTransactionJob`, `handleFailedTransactionJob`, injected deps) and unit-tested without Redis in `transaction.worker.test.ts`.
  - *Batch token whitelist (P2):* `POST /v1/transactions/batch` never passed the action `token` to `validateTransaction`, so the off-chain `allowedTokens` whitelist did not apply. The caller-declared token is now checked; an agent with a non-empty whitelist must declare a token on every action with calldata (`400 { error: "token is required for this action because the agent has a token whitelist", actionIndex }`); `token` must be a 40-hex address. Route comment and OpenAPI `BatchRequest` say the token is caller-declared and `allowedContracts` is the binding control for raw calldata.
  - *Simulation error order (P3):* `isRpcTransportFailure` walked the viem cause chain for `InternalRpcError` before looking for a revert, so RPCs that wrap reverts in `-32603` (`EstimateGasExecutionError → ExecutionRevertedError → InternalRpcError → RpcRequestError`) were reported as "service unavailable". Reverts (`ExecutionRevertedError`, `ContractFunctionRevertedError`, RPC code `3`) are classified first and return a failed simulation with the reason.
  - *Guard vs simulator on staging (P3):* `simulation-guard.ts` only rejected a mock under `production`; it now uses the shared `isProductionLikeEnv()` (`config/runtime-env.ts`), matching the simulator (`production` + `staging`).
  - *Legacy executor (P3):* a configured `EXECUTOR_ADDRESS_<chainId>` that is a known pre-October-2026 deployment only produced a WARN while every routed tx reverted. `production`/`staging` now refuse to boot (`FATAL` in `env.ts`); in development `getContracts().executor` / `ExecutorService` treat it as not configured (route direct, `routedViaExecutor=false`) and log once. `findLegacyContractConfig` / new `resolveExecutorAddress` take an injectable env and are unit-tested.
  - *Preflight wording (P3):* `scripts/preflight.ts` no longer fails without Tenderly saying "simulations will be skipped"; it WARNs with the same wording as `env.ts` (eth_call fallback).
  - *Public self-registration (P3):* `POST /v1/public/agents` accepted an arbitrary initial `policy` from an unauthenticated caller. It is now ignored and the server defaults are forced (like `tier`).
  - *Docs/spec:* operator secret documented on `PATCH /v1/agents/:id/policy`; `503 SimulationUnavailable` shared response on every simulating transaction operation; strict decimal `pattern` on `Policy`; `UpdatePolicyRequest.reason` (audit log only — the MCP `update_policy` tool now actually sends it); generated types regenerated.
- **Admin kill switch now stops transactions that were already queued.** The BullMQ transaction worker used to mark a job SUBMITTED and sign/broadcast it without re-reading the agent, policy or transaction state, so a tx enqueued seconds before `POST /admin/agents/:id/pause` was still broadcast. New `services/transaction/pre-submit-guard.ts` re-reads the transaction (`status`, `txHash`), its agent (`active`) and policy (`active`, `expiresAt`) in one Prisma query before submission: a tx that is no longer `QUEUED` or already has a `txHash` is skipped (idempotency guard for retries/redelivery); a tx whose agent is inactive, whose policy is inactive, or whose policy has expired is marked `FAILED` (`error: "Agent paused before submission"` / `"Agent policy expired before submission"`) and the worker returns without throwing so BullMQ does not retry it. Blocked A2A payments are finalized as `PAYMENT_FAILED` through the existing finalizer, which refunds the escrow reservation. 14 unit tests in `transaction.worker.guard.test.ts`.
- **Backend AgentExecutor ABI matches the Solidity source (A1).** `AgentExecutor.Action` has been `(target, value, token, data)` since `e0c8025` (2026-04-06), but `executor.service.ts` still encoded `(target, value, data)` — wrong selectors (`0xa60e5271`/`0x34fcd5be` instead of `0x596e8b81`/`0x672093df`), so anything routed through a freshly deployed executor would revert. The ABI is now generated from Foundry into `packages/backend/src/abi/AgentExecutor.abi.ts` (`npm run abi:executor`) and shared by `executor.service.ts`, `/v1/transactions/batch` and the admin batch route. `TransactionData` gained an optional `token` that the builder fills (tokenIn for Uniswap/Curve, asset for Aave/Compound/ERC-4626, token for transfers/approvals, collateral for GMX, zero address for ETH) and the wrapper forwards as `Action.token`. New unit test `executor.service.test.ts` pins both selectors, decodes the encoded actions, and diffs the checked-in ABI against the Foundry artifact when `packages/contracts/out/` exists.
- **x402 buyer client hardened after review R3 (F1–F9).** A blank `X402_FACILITATOR_URL=` in `.env` no longer aborts boot (`config/env.ts` preprocesses `""` to unset; `.env.example` ships the line commented out; new `env.example.test.ts` boots the real schema from the shipped example). `X402ClientService.payResource` now requires explicit `allowedNetworks` (exact CAIP-2 ids — wildcards only with `allowWildcardNetworks: true`, no more `eip155:*` default), refuses before signing any option whose `maxTimeoutSeconds` exceeds `MAX_AUTHORIZATION_WINDOW_SECONDS` (600 s, overridable) so a server cannot obtain a years-long authorization, surfaces the signed authorization (`nonce`, `validAfter`, `validBefore`, `method`) and `paymentIdSent` on results and on every `PaymentFailedError` after signing, applies a 30 s per-phase timeout (`requestTimeoutMs`, `details.timedOut`), strips query strings/userinfo from error messages and clips server reasons at 200 chars, and marks receipts unverified when the signed offer names a different resource than the 402 or had expired before signing. `TurnkeyService.signDigest` accepts `v` as `00/01` or `1b/1c` and always emits 27/28. Docs (`docs/architecture/x402-payments.md`) state that the client re-signs on every call and that P5 must not retry a `paymentId` with `authorizationSent: true` until reconciled. 36 + 8 + 3 tests cover each change.

The comment is gone; the route now accepts an optional body `{ "syncOnChain": true }` and, when the agent's chain has a policy module, returns `onChainSync: { to, chainId, actions, notice }` carrying `AgentPolicyModule.emergencyPause(safe)` (or `resume(safe)` when toggling back) calldata for the operator to broadcast via `/admin/transactions/batch` — same contract as `PATCH /v1/agents/:id/policy`. ### Security

- **MCP tool errors are sanitized before they reach the client (S2).** `@agent_fi/mcp-server` returned `err.message` verbatim, and backend error bodies can carry viem errors with the RPC URL (Alchemy/Infura key in the path), Prisma messages with container file paths, internal hosts and stack frames. Every error now leaves the single `tools/call` dispatcher through `src/errors.ts`: the backend message, `code` (including codes the backend puts in `error`, e.g. `ESCROW_NOT_FUNDED`), HTTP `status` and structured details are kept; internal and credentialed URLs (the configured `AGENTFI_API_URL`, private/loopback/`.internal` hosts, any URL with userinfo or a query string, RPC keys in the path), private IPs, stack frames, file paths, values of secret-named env vars, the agent's `AGENTFI_API_KEY` and any `agfi_` key, bearer tokens, labelled secrets and 32-byte hex after a key-ish word are stripped from the message and every string in the details (a bare tx hash or `deliverableHash` survives); `stack` fields are dropped. Invalid tool input becomes `INVALID_INPUT` with the Zod issues, a network failure `UPSTREAM_UNREACHABLE`. Each error result carries a random 12-hex `traceId`, and the full original error is logged to stderr with the same id. `pay_for_resource` typed refusals (`BUDGET_EXCEEDED`, `PAYMENT_OUTCOME_UNKNOWN`, …) are still structured output, and its S4 target refusals (`INVALID_URL`, `REDIRECT_REFUSED`) keep `hostname`/`address`/`location` (secret rules still apply). `ApiError` moved to the side-effect-free `src/api-error.ts` (re-exported from `api-client.ts`).
- **`POST /v1/jobs/:id/pay-resource` can no longer be used to reach internal services (S4, automated security review of #144).** The route fetches an agent-chosen URL and returns up to 64 KiB of the answer, but its private-host guard only inspected the literal hostname, only ran in production/staging, and the fetch followed redirects — so a provider agent could read cloud metadata (`169.254.169.254`), the Postgres/Redis ports or the loopback admin API through a public DNS name resolving to a private address, a redirect, or a DNS rebind. Now, in every environment: (1) the hostname is resolved before connecting (`dns.promises.lookup`, all addresses, verbatim) and refused when the host is, or **any** resolved address is, loopback / private / link-local / unique-local / unspecified / reserved, with IPv4-mapped and NAT64 addresses judged as IPv4 (`400 INVALID_URL` with `refusal`, `hostname`, `address`; a transient DNS failure is `502 PAYMENT_FAILED`, `stage: "resolve"`); (2) the connection is pinned to the validated addresses through a per-request undici `Agent` whose `connect.lookup` answers nothing else (`Host` / SNI unchanged); (3) redirects are never followed — any `3xx` is the new `400 REDIRECT_REFUSED` (before signing: nothing recorded; after signing: row `refused`, or `settled` when the server reported a settlement on the redirect). New `services/payments/outbound-target.ts` (`assertPublicTarget`, `isPrivateAddress`, `pinnedLookup`, `createPinnedDispatcher`). `X402ClientService` defaults to `redirect: 'manual'`, forwards `init.dispatcher` on every transport call, and its default transport is now the `undici` package's own `fetch` (new dependency `undici` ^7.30), so the pinned Agent is never driven by a different undici major bundled in Node. New `RESOURCE_PAYMENT_ALLOW_PRIVATE_HOSTS` (default `false`, documented in `.env.example`) lifts only the range refusal for a resource server on localhost during development; boot is `FATAL` with `true` in production/staging. Also fixes the old literal check missing IPv4-mapped literals in the hex form URL parsing produces (`[::ffff:7f00:1]`). OpenAPI (`REDIRECT_REFUSED`, `refusal`/`hostname`/`address`/`location`, `stage: resolve`) and generated types, `docs/api-reference.md`, `docs/architecture/x402-payments.md` §10. New tests: `outbound-target.test.ts`, `resource-payment.target-policy.test.ts` (override unset), redirect and end-to-end pinning cases in `resource-payment.routes.test.ts`, boot-guard cases in `env.example.test.ts`.
- **Agents can no longer loosen their own policy (S1).** `PATCH /v1/agents/:id/policy` only checked that the caller was the agent itself, so an agent — or a prompt-injected one — could raise `maxValuePerTxEth`, clear its whitelists, drop its cooldown, re-activate a paused policy or remove its expiry. The route now enforces *tighten-only for agents, operator may loosen*: a pure `classifyPolicyChange()` (`packages/backend/src/services/policy/policy-authority.ts`) flags each loosened field, the agent gets `403 { error, loosenedFields }`, and the operator (`x-api-key: <API_SECRET>`, now also accepted on this route by the auth middleware) may set any policy on any agent. Every policy write logs `agentId`, caller kind and changed fields. The `update_policy` MCP tool description now says it can only tighten. OpenAPI: operation description, `403` schema (`PolicyChangeForbidden`), `404`, `operatorApiKey` security; generated types regenerated.
