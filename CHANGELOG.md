- **Job-scoped x402 payments: `POST /v1/jobs/:id/pay-resource` + MCP `pay_for_resource` (P2, with the P5 ledger state machine).** The job's **provider** pays a third-party HTTP 402 resource with its own USDC, within the job's remaining reward budget (`reward − Σ reserved/pending/settled/unknown payments`); the requester gets `403`, a job that is not `ACCEPTED` gets `409`, and only USDC-denominated jobs qualify (`400 UNSUPPORTED_BUDGET_TOKEN` — no oracle conversion). The cap (remaining budget, lowered by the caller's `maxAmount`) is handed to `X402ClientService`, so an above-cap price is refused **before anything is signed** (`402 BUDGET_EXCEEDED` with `price`/`remaining`/`cap`); only USDC on the job's chain is accepted (`400 UNSUPPORTED_ASSET`). Every attempt is a durable `ResourcePayment` row (migration **0016**, model at the end of `schema.prisma`; `(jobId, paymentId)` unique) with the state machine `reserved → pending → settled | unknown | refused` plus `failed_before_signing`: the row is reserved under a `Job` row lock before signing (concurrent payments cannot overspend), the EIP-3009 nonce is recorded before the signed payload leaves, a timeout / transport error after signing is `unknown` (502 `PAYMENT_OUTCOME_UNKNOWN`, counted against the budget, logged for the operator, **never retried automatically**), and an `offer-receipt` that does not verify still settles but is stored `receiptVerified: false`. Idempotent per `paymentId` (sent to the server through the x402 `payment-identifier` extension): a retry returns a `pending`/`settled`/`unknown` row without a second payment; `refused`/`failed_before_signing` rows are retried on the same row. The URL is stored without query string or userinfo; the signed authorization is never echoed. `X402ClientService` gained the `onBeforeSign` / `onAuthorizationSigned` ledger hooks (a throw aborts before signing / before sending); the P1 fake-facilitator harness moved to `src/__tests__/helpers/x402-fixture.ts`; the token registry gained Base Sepolia USDC. ### Fixed

- **ERC-8183 escrow: the chain is the source of truth (C3c, second adversarial review, absorbs N1).** (1) *A Transaction row no longer unwinds a step.* The confirmation monitor is a promise inside the worker and marked a transaction FAILED after ~7.5 minutes without a receipt; a `fund` "FAILED" while mined failed the job and released the reservation with the USDC locked and no refund path, a lost `fund` monitor left the job `APPROVED` forever (provider `409`, no cancellation refund, ignored by the expiry sweep), a lost `submit` monitor got the provider refunded away at expiry, a lost identity monitor blocked the provider's binding lane. Now every failed step reads `getJob` first and advances from the chain (an unreadable chain unwinds nothing), every step advance is a conditional write so replays run their effects once, the monitor leaves a receipt-less transaction `SUBMITTED` instead of FAILED, receipts are recorded with a conditional write and only that observer runs the outcome, and `repollSubmittedTransactions` re-reads `SUBMITTED` rows at every worker boot and on every payment-recovery tick (`TX_REPOLL_STALE_SEC`, default 600 s; a transaction no node knows is FAILED only after `TX_DROP_AFTER_SEC`, default 1800 s). The payment-recovery tick also reconciles stale escrow jobs from the chain (`reconcileEscrowJobs`, `ESCROW_RECONCILE_STALE_SEC`, default 600 s): stalled funding steps resume, lost cancellation refunds are re-enqueued, deliverables Submitted on-chain are settled, stuck bindings resume. The expiry sweep claims every on-chain job past `expiresAt` that is not final in the DB (Open ones close as the new `onChainStatus` `EXPIRED_UNFUNDED`). The submitter recognises a broadcast whose RPC answer was lost (local hash looked up) instead of signing a second transaction that reverts. (2) *Payment recovery runs in `worker.ts`* — the documented API + worker topology never ran it; the BullMQ repeat id dedupes the schedule across processes; the worker split into `worker-process.ts`, shutdown drains monitors for 10 s. (3) *Two concurrent `PATCH COMPLETED` gave the requester the result and a refund* (reproduced 9/10): `PATCH /v1/jobs/:id` transitions are conditional on the status read (`409 JOB_STATUS_CONFLICT`, no side effects for the loser; an escrow ACCEPT also requires `onChainStatus = FUNDED` in the same write), a job is handed back to `ACCEPTED` only when no `submit` of it is live, `settle` acts on a job Submitted on-chain even when the DB disagrees, and a cancellation never rejects a job Submitted on-chain (refused, `escrowError`, `ESCROW_ALERT`). (4) *Allowance overwrite and nonce collisions:* one serial **funding lane** per requester and chain (`approve` → `fund` of one job at a time, exact per-job approvals) and one **broadcast lane** per wallet (Redis lock from the nonce read to the broadcast, `pending` nonce plus the last broadcast nonce for 60 s) — a requester funding two jobs, an agent that is both requester and provider, a bind next to a submit, two retried submits. (5) A cancellation refund is scheduled for every job that exists on-chain (the reject reads the chain) and re-enqueued by recovery when it was lost; the evaluator's native balance is checked before each send and alerted below `ESCROW_EVALUATOR_MIN_BALANCE_WEI` (default 0.0005 ETH). New notification type `ESCROW_ALERT`; new `services/transaction/wallet-lane.ts` (+ `.runtime.ts`). Postgres-backed suites (`*.db.test.ts`) now run in their own sequential pass after the main one (`npm test`; `npm run test:db` alone). Tests: `escrow-chain-truth.db.test.ts` (19, against Postgres with the real route, orchestrator, processor, submitter, monitor, finalizer and recovery tick, a simulated chain with nonces/mempool/signed transactions; every review scenario, the concurrent-completion one looped 10×; each of nine fixes was reverted once to check a test fails), `wallet-lane.test.ts`, `transaction.repoll.test.ts`, `worker-process.test.ts`, C3c blocks in the orchestrator, route and recovery suites. Docs: `erc-8183-mapping.md` §6.4 and §6.7, `erc-8004-integration.md` §7.3/§7.5, `production-deploy.md` worker topology, release runbook, setup checklist.
- **`ReputationHook` can no longer lose the ERC-8004 feedback to gas estimation (R3c, contract change before C4).** The hook wraps its registry calls so a registry can never block settlement, which let `eth_estimateGas` converge on the limit at which `giveFeedback` runs out of gas inside the `try` (C5a: estimate 246 770 → `FeedbackFailed`, payment settled without feedback) for *any* caller that trusts estimation, not only AgentFi's evaluator. Now (1) every registry call forwards a fixed gas cap — new constructor immutables `feedbackGasLimit` (`giveFeedback`) and `identityCallGasLimit` (each `ownerOf` / `getAgentWallet` static call), bounds-checked (`InvalidFeedbackGasLimit` 250 000–2 000 000, `InvalidIdentityCallGasLimit` 20 000–200 000); (2) once the cheap gates pass, the hook requires `gasleft() >= feedbackGasRequirement` (both caps, EIP-150's 1/64, reserves; 667 937 with the defaults) and, right before `giveFeedback`, that the call gets its full cap, otherwise the whole `complete` / `reject` reverts with `InsufficientGasForFeedback(available, required)` — this depends only on the caller's gas, so the lowest gas at which settlement succeeds now writes the feedback and an under-gassed call fails loudly; (3) a registry that burns gas costs at most its cap and still cannot block settlement (no "callee used all its gas" revert), and return data is never copied beyond 32 bytes (identity) / 256 bytes (`FeedbackFailed.reason`, now truncated), so a return-data bomb cannot inflate the hook's cost. Jobs whose gates skip the write are unaffected; `claimRefund` (not hooked) stays the unconditional escape hatch. `decodeFeedbackParams` (self-call, trusted-evaluator input, own `pure` code) is deliberately not capped. `script/DeployEscrow.s.sol` reads `FEEDBACK_GAS_LIMIT` (default 500 000 = 2.7× the 183 416 a cold first `giveFeedback` costs on the v2.0.0 registry) and `IDENTITY_CALL_GAS_LIMIT` (default 50 000 = 6.4× the ~7 800 of `ownerOf` / `getAgentWallet`) and refuses out-of-bound values before broadcasting (`InvalidGasLimit`). 21 new Foundry tests (312 + 1 skipped): binary-searched minimal gas writes the feedback for `complete` / `reject` (plus a fuzz over URI length) and one unit below reverts with the guard; gas-burning reputation and identity registries, a revert-data bomb and a 64 KiB identity return leave the minimal gas unchanged and settle (`FeedbackFailed` / `agent-not-provider`); the worst case (both identity caps burnt + 40 KB URI) still writes; every cheap-gate skip settles with 200 000 gas; deploy-script bounds. New `test/ReputationHook.fork.t.sol` checks the property against the real registries on a Base Sepolia fork (skipped without `BASE_SEPOLIA_FORK_URL`). Backend ABI regenerated; `EVALUATOR_GAS_HEADROOM` kept as insurance. Docs: `erc-8004-integration.md` §4 "Gas policy", `contract-deployment.md`, `testnet-log.md` §2 / §5.3.
- **No ERC-8183 settlement could ever be enqueued (found by the C5a fork rehearsal).** The escrow settlement queue added every evaluator action with BullMQ `jobId = "<action>:<jobId>"`; BullMQ 5 rejects a custom id containing `:` unless it splits into exactly three parts, so every `complete` / `reject` / `claimRefund` enqueue threw `Custom Id cannot contain :`. Funded jobs reached `SUBMITTED` and stayed `PAYMENT_PENDING` forever; cancellation and contest refunds and the expiry sweep failed the same way (the orchestrator unit tests inject a fake queue, so they never hit BullMQ's validation). Ids are now `<action>-<jobId>`; `escrow-settlement.queue.test.ts` runs BullMQ's own `Job.validateOptions` on them.
- **Evaluator settlements silently lost the ERC-8004 feedback (found by the C5a fork rehearsal).** `complete` / `reject` run `ReputationHook.afterAction`, which calls the Reputation Registry inside a try/catch so a registry failure never blocks settlement. The evaluator signer sent viem's default gas — the bare `eth_estimateGas`, i.e. the lowest limit at which the tx succeeds — and at that limit `giveFeedback` runs out of gas, the hook catches it and emits `FeedbackFailed(jobId, "")`: payment settled, feedback lost on every job. Measured on the fork: estimate 246 770 → `FeedbackFailed`; the full path uses 340 231 (`giveFeedback` 179 416). The signer now sends `estimate + EVALUATOR_GAS_HEADROOM` (400 000; unused gas is not charged); `evaluator-signer.test.ts` pins it. The contract-side fix for every other caller followed before C4 (R3c, entry above).
- **The stdio MCP server no longer writes to stdout at startup (found by S2).** `api-client.ts` loaded `dotenv/config`, and dotenv 17 prints `◇ injected env (n) from .env // tip: …` to stdout via `console.log` — on the stdio transport stdout is the JSON-RPC channel, so every client saw a non-JSON line before `initialize`. It now calls `config({ quiet: true })`; `stdio.test.ts` spawns the server and fails on any non-JSON-RPC stdout line.
- **Admin resume re-activates the DB policy the pause deactivated (A3b).** Resuming an agent through the `POST /admin/agents/:id/pause` toggle only flipped `agent.active`; `AgentPolicy.active` stayed `false`, so the agent remained blocked by `PolicyService.validateTransaction` and the worker's pre-submit guard until someone remembered a `PATCH /v1/agents/:id/policy`. The pause now stamps `AgentPolicy.pausedByOperatorAt` (migration `0017_policy_pause_marker`) when it deactivates an *active* policy, and resume re-activates the policy only while that stamp is present, then clears it — a policy that was already inactive before the pause (agent soft-delete via `DELETE /v1/agents/:id`, `PATCH active=false`, or a pause that predates the stamp) stays inactive and the response says so. Any explicit `active` write through `PolicyService.setPolicy` and the soft-delete path clear the stamp, so a later resume can never undo a deactivation it did not cause. New explicit, idempotent `POST /admin/agents/:id/resume` (same `{ syncOnChain }` body; no-op on an agent that is not paused); both resume paths answer `{ active: true, agentReactivated, policyReactivated, policyNote, onChainSync }` where `onChainSync` carries `AgentPolicyModule.resume(safe)` calldata on request. The pause response is unchanged. The admin dashboard's Pause/Resume button shows `policyNote` when the policy was left inactive. OpenAPI (`ResumeAgentResponse`, `PausedAgentResponse`, `Policy.pausedByOperatorAt`) and generated types updated. 24 new tests in `admin.pause.routes.test.ts` (route + pre-submit guard end to end, calldata decoded against the ABI) and `policy.service.test.ts`.
- **No mock simulation can authorise a transaction in production or staging (A2).** `SimulatorService` used to return an always-success stub whenever Tenderly was not configured — in every environment. Now, without Tenderly, `NODE_ENV=production`/`staging` run a real `eth_call` dry-run (viem `estimateGas` against the chain RPC, provider `'eth_call'`): a revert is a failed simulation with the reason, an RPC/transport failure throws `Simulation service unavailable … Transaction blocked for safety`, and only `development`/`test` keep the mock (`provider: 'mock'`, `_isMock: true`). New `services/transaction/simulation-guard.ts` (`isSimulationUsable` / `assertSimulationUsable` / `ensureSimulationUsable`) is called by every transaction route and the A2A payment path as defense in depth: a mock result in a production-like environment is refused with `503 { error: "Simulation unavailable in production" }`. `env.ts` logs a WARN at boot when production runs without Tenderly. `simulator.service.test.ts` covers all providers and the guard.
- **Review follow-ups to A1/A2/A3/S1 (`fix/review-r1-backend`).**
  - *S1 bypass (P1):* an agent could `PATCH` `maxValuePerTxEth: ""` (or `"  "`, `"1e3"`, `"0x10"`, `"5abc"`, `"unlimited"`): the tighten-only classifier read it with `Number()` (→ `0`, "tightening") while `PolicyService` enforced with `parseFloat()` (→ `NaN`, no limit). Both halves now share one parser (`services/policy/policy-numbers.ts` — `parsePolicyDecimal`, where an unparsable value is *unlimited* and therefore always loosening), and the API edge (`createAgentSchema`, `updatePolicySchema`, `POST /v1/public/agents`, the MCP `update_policy` tool) only accepts the strict pattern `^\d+(\.\d+)?$` — anything else is `400`. Zod failures on these routes are now `400 { error: "Validation failed", details }` instead of an unhandled 500.

- **`POST /v1/jobs/:id/pay-resource` can no longer be used to reach internal services (S4, automated security review of #144).** The route fetches an agent-chosen URL and returns up to 64 KiB of the answer, but its private-host guard only inspected the literal hostname, only ran in production/staging, and the fetch followed redirects — so a provider agent could read cloud metadata (`169.254.169.254`), the Postgres/Redis ports or the loopback admin API through a public DNS name resolving to a private address, a redirect, or a DNS rebind. Now, in every environment: (1) the hostname is resolved before connecting (`dns.promises.lookup`, all addresses, verbatim) and refused when the host is, or **any** resolved address is, loopback / private / link-local / unique-local / unspecified / reserved, with IPv4-mapped and NAT64 addresses judged as IPv4 (`400 INVALID_URL` with `refusal`, `hostname`, `address`; a transient DNS failure is `502 PAYMENT_FAILED`, `stage: "resolve"`); (2) the connection is pinned to the validated addresses through a per-request undici `Agent` whose `connect.lookup` answers nothing else (`Host` / SNI unchanged); (3) redirects are never followed — any `3xx` is the new `400 REDIRECT_REFUSED` (before signing: nothing recorded; after signing: row `refused`, or `settled` when the server reported a settlement on the redirect). New `services/payments/outbound-target.ts` (`assertPublicTarget`, `isPrivateAddress`, `pinnedLookup`, `createPinnedDispatcher`). `X402ClientService` defaults to `redirect: 'manual'`, forwards `init.dispatcher` on every transport call, and its default transport is now the `undici` package's own `fetch` (new dependency `undici` ^7.30), so the pinned Agent is never driven by a different undici major bundled in Node. New `RESOURCE_PAYMENT_ALLOW_PRIVATE_HOSTS` (default `false`, documented in `.env.example`) lifts only the range refusal for a resource server on localhost during development; boot is `FATAL` with `true` in production/staging. Also fixes the old literal check missing IPv4-mapped literals in the hex form URL parsing produces (`[::ffff:7f00:1]`). OpenAPI (`REDIRECT_REFUSED`, `refusal`/`hostname`/`address`/`location`, `stage: resolve`) and generated types, `docs/api-reference.md`, `docs/architecture/x402-payments.md` §10. New tests: `outbound-target.test.ts`, `resource-payment.target-policy.test.ts` (override unset), redirect and end-to-end pinning cases in `resource-payment.routes.test.ts`, boot-guard cases in `env.example.test.ts`.
- **Agents can no longer loosen their own policy (S1).** `PATCH /v1/agents/:id/policy` only checked that the caller was the agent itself, so an agent — or a prompt-injected one — could raise `maxValuePerTxEth`, clear its whitelists, drop its cooldown, re-activate a paused policy or remove its expiry. The route now enforces *tighten-only for agents, operator may loosen*: a pure `classifyPolicyChange()` (`packages/backend/src/services/policy/policy-authority.ts`) flags each loosened field, the agent gets `403 { error, loosenedFields }`, and the operator (`x-api-key: <API_SECRET>`, now also accepted on this route by the auth middleware) may set any policy on any agent. Every policy write logs `agentId`, caller kind and changed fields. The `update_policy` MCP tool description now says it can only tighten. OpenAPI: operation description, `403` schema (`PolicyChangeForbidden`), `404`, `operatorApiKey` security; generated types regenerated.
